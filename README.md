# aimobility-junseo-practice

대전 BIS 버스 **정류장 간 통행시간(`tt_sec`) 예측** 연습용 데이터(`bis-travel-time-practice`)로, 베이스라인 노트북에서 출발해 **앙상블 직전까지** 진행한 분석·실험 기록임.

- 직접 실행해 볼 수 있는 노트북: [`notebooks/junseo_practice.ipynb`](notebooks/junseo_practice.ipynb) (실행 결과가 저장되어 있음)
- 아래는 어떤 순서로, 무엇을 확인했고, 어떤 결과가 나왔는지의 기록임. 점수가 나빠졌거나 효과가 없던 실험도 함께 적음.

---

## 1. 과제와 평가 방식

| 항목 | 내용 |
|---|---|
| 예측 대상 | 출발 정류장 도착 → 다음 정류장 도착까지 걸린 시간 `tt_sec`(초) |
| 지표 | MAE (같으면 RMSE). 기준선은 "같은 노선·방향·정류장 순번·시간대 평균" 예측 |
| 허용 모델 | 앙상블 계열(XGBoost, LightGBM, CatBoost, RandomForest 등) |
| 외부 데이터 | 사용 금지 |
| 검증 | 학습 데이터를 **날짜 단위**로 나눔 (무작위 분할 금지) |
| 데이터 | train 109,891행(월 28,783 / 화 28,870 / 수 28,887 / 토 23,351), test 79,942행(목 28,853 / 금 28,713 / 일 22,376), 노선 4개(1, 102, 511, 605), 차량 89대 |

핵심 구조: **train은 월·화·수·토, test는 목·금·일** → 처음 보는 날짜를 맞히는 문제이고, 일요일은 학습에 없음.

## 2. 진행 순서

1. 베이스라인 노트북 읽기 / 이해
2. 데이터 분석 — 버스(차량)별, 요일별, 시간대별, 데이터 품질
3. 검증 설계와 기준선 (날짜 단위, 시드 흔들림 측정)
4. 오차 분석 — 어디서 많이 틀리는가
5. 피처 실험 — 후보를 하나씩 넣어 비교
6. 하이퍼파라미터 조정
7. 조정 후 설정에서 피처 재검증
8. (다음) 앙상블

## 3. 데이터 분석 결과

### 3-1. 정답 `tt_sec`
- 분위수: 1% 22 / 5% 33 / 25% 56 / **50% 89** / 75% 150 / 95% 256 / 99% 534초
- **600초 초과 938행(0.85%)** — 상위 10개 구간이 97%를 차지하는, 한 곳에서 오래 기다리는 구간
- 평균 속도 15.5km/h. 정류장 간 거리가 짧을수록 느림 (200m 이하 13.3km/h, 800m 이상 약 19km/h → 정차 시간 비중이 커서)

### 3-2. 버스(차량)별
| 확인 | 결과 |
|---|---|
| 노선을 넘나드는 차량 | 없음 (89대 모두 한 노선) |
| test 차량이 train에도 있는가 | 99% |
| 빠른/느린 버스 차이 | 차량 효과 표준편차 0.018 (약 ±2%) |
| 그 차이가 날짜가 바뀌어도 유지되는가 | 시간대 보정 후 상관 0.11~0.47 (약함) |
| 차량-일 효과를 알면 줄어드는 분산 | 0.7% |

→ **버스별 차이는 거의 없음.** 버스별 가중치는 줄 이유가 없음.

### 3-3. 요일별
| 날짜 | 평균 tt(초) | 중앙값 | 평소(구간 전체 중앙값) 대비 | 변동폭(로그비 std) |
|---|---|---|---|---|
| 월 | 111.8 | 89 | +0.5% | 0.377 |
| 화 | 112.0 | 90 | +1.3% | 0.377 |
| 수 | 111.9 | 90 | +1.0% | 0.371 |
| 토 | 111.4 | 85 | −2.5% | 0.448 |

- 월·화·수는 사실상 같은 날. 토요일만 다름 (중앙값이 낮고 변동폭이 큼).
- 구간별 중앙값의 날짜 간 상관: 평일끼리 0.98~0.99, 평일–토 0.91~0.93. **구간×시간대** 중앙값은 평일끼리 0.89~0.92, 평일–토 0.69~0.72 → 구간 자체의 성격은 유지되지만 시간대별 모양은 주말에 많이 달라짐.
- 이름이 같은 구간(`same_name`)의 평균 tt: 평일 약 465초, 토요일 378초.
- 운행량(시간대별 행 수): 일요일(test 입력)은 토요일과 거의 같음 (일 22,376행 / 토 23,351행).

### 3-4. 시간대별
- 평소 대비: 5시 −17%, 22시 −20%, 23시 −29% (가장 빠름), 오전 8시 +7%, **오후 15~18시 +7~+12%** (17시 최고).
- 평일은 8시와 17~18시에 평균 통행시간 피크, 토요일은 출근 피크 없이 낮 14시(약 133초)가 가장 느림.
- 노선마다 피크 강도가 다름 (17시 기준 102번 +14%, 511번 +16%, 605번 +11%, 1번 +7%).
- 변동폭은 시간대와 무관하게 거의 일정 (로그비 std 0.36~0.42).
- 현재 `is_peak`(7~9, 17~19시)는 데이터와 어긋남: 7시 약 0%, 19시 약 +1%이고 15~16시가 빠져 있음. (가설 단계, 학습 폴드 기준으로 재검증 필요)

### 3-5. 데이터 품질
- 중복·결측 없음. test에서 train에 없는 구간은 **2행뿐**.
- 연속 행의 이전 `to_stop` == 현재 `from_stop`: 100% 일치.
- 같은 차량·방향에서 `stop_seq`가 건너뛰는 지점(끊김) 818군데 = 연속 행 쌍 106,110개 중 **0.77%** (영향은 작음).
- 시속 60km 초과 164행, 도로 거리가 직선 거리의 90%보다 짧은 행 154개 (둘 다 0.2% 미만).

## 4. 검증 설계 (실험 규칙)

- **날짜 하나를 통째로 빼고 나머지로 학습**, 4번(월·화·수·토) 반복.
- 점수는 **월·화·수 평균 / 토요일 / 4일 평균**을 항상 따로 기록. 토요일 검증은 학습에 평일만 있는 조건이라 **일요일 성능이 아님**.
- 모델·피처 선택은 **월·화·수 평균**으로, 토요일은 참고용.
- **채택 규칙**: 월·화·수 평균 −0.10 이상 개선 + 세 날 모두 개선.
- **시드 3개(0, 1, 2)** 평균으로 비교. 시드만 바꿨을 때 흔들림: 월·화·수 평균 표준편차 0.018(최대−최소 0.035), 토요일 표준편차 0.149(0.285) → 이보다 작은 차이는 결론으로 쓰지 않음.
- **누수 방지**: 정답으로 뽑는 통계(예: 느린 구간 목록)는 폴드의 학습 날짜에서만 계산하고, 학습 행에 넣는 값은 자기 날짜를 뺀 나머지 날짜로 계산.
- 트리 개수는 검증 날짜로 early stopping하지 않고, 한 번 학습한 뒤 중간 시점에서 잘라 비교.
- 연습용 `test`는 **마지막 확인용** — 모델 선택에 쓰지 않음 (확인은 후보 1회 + 현재 설정 1회).

### 기준선 (날짜 단위 검증, MAE)
| | 월 | 화 | 수 | 토 | 월화수 평균 |
|---|---|---|---|---|---|
| 평균 예측 (모델 없음) | 29.53 | 28.46 | 28.71 | 37.57 | 28.90 |
| LightGBM (leaves127, mcs50, 500트리) 시드3 평균 | 26.93 | 26.07 | 26.15 | 36.77 | **26.383** |

## 5. 오차 분석

정답 크기별·노선별·시간대별은 수요일을 빼고 학습한 모델(수요일 폴드) 기준, "600초 초과 / 이름 같은 구간의 오차 비중"은 4개 폴드를 합친 값.

- **노선별**: 1번이 가장 큼(MAE 33), 102/511/605는 약 25~27.
- **정답 크기별**: 정답이 480초를 넘는 행은 1.2%뿐인데 오차의 9.4%를 차지, 240초 초과 구간은 오차의 약 20%.
- **종점·대기성 구간**: 출발·도착 정류장 이름이 같은 구간(1,530행, 1.39%)은 평균 446초, 표준편차 412초. **600초 초과 행이 전체 오차의 7.9%, 이름 같은 구간이 8.0%, 둘을 합치면 11.8%** — 즉 오차의 약 88%는 일반 구간의 잡음임.
- 느린 구간 후보: 구간 중앙값 속도 1.5m/s 미만(n≥30)인 구간은 4개이고, 모두 방향 0의 마지막 또는 마지막에서 두 번째 정류장 부근임 (노선 끝부분과 일치하는 정황이지만 "회차"로 단정하지 않고 `is_slow_segment` 후보로 부름).
- 같은 날·같은 구간·시간대 중앙값으로 맞춰도 MAE 21.65(정답을 쓰는 값이라 실제로는 못 씀) → **같은 구간·시간대에서도 버스마다 달라지는 잡음이 커서 한계가 높음.**

## 7. 현재 설정과 성능

**설정**: `objective=regression_l1`, `learning_rate=0.05`, `n_estimators=1000`, `num_leaves=127`, `min_child_samples=10`, `subsample=0.8`(freq 1), `colsample_bytree=0.8`, `reg_lambda=0`. 피처는 노트북 기본 14개 + `route_id`(범주형).

## 8. 한계와 주의

- **일요일은 검증할 방법이 없음.** 학습에 주말은 토요일 하루뿐. 월·화·수에서 좋아진 만큼 일요일에서도 좋아진다는 보장이 없음 (실제로 test 개선폭은 검증의 약 절반인 −0.22).
- 설정을 월·화·수 점수로 골랐기 때문에 **선택 낙관**이 있음.
- 토요일 폴드는 시드·피처에 따라 쉽게 움직임 (시드 표준편차 약 0.15).
- 이 숫자는 연습용 노선(1, 102, 511, 605) 기준이고, 대회는 노선 5개로 달라 오차 크기가 다를 수 있음.
- 직전 구간의 실제 `tt_sec`을 쓰는 lag 피처는 대회 test에 정답이 없어 쓸 수 없고, "다음 행의 `arrive_hour`"로 정답을 간접 추정하는 방식은 규칙(정답 추정 금지)에 걸릴 수 있어 쓰지 않음.

### 중간에 정정한 내용 (기록용)
- "대기 구간이 오차의 가장 큰 덩어리"라고 했으나 재현해 보니 약 12%였고 나머지 88%는 일반 구간 잡음이었음.
- "끊김 818군데가 trip 피처가 안 먹힌 이유일 수 있다"고 했으나 연속 행 쌍의 0.77%라 근거가 약함 → 철회.
- "min_child_samples=20이 가장 효과적"은 `num_leaves` 효과와 섞여 있었음 → 6-2에서 분리했고 둘 다 기여.
- 용량을 키우면 토요일이 나빠진다는 말은 시드 흔들림 범위 안이라 확정할 수 없음.
- 평일·주말 피크 정의, "월·화·수는 같은 날" 등은 전체 train으로 본 기술 통계라 **가설**이며 학습 폴드 기준 검증이 필요.
